01 · Problema e solução

A ideia em uma frase

O UFABC Zipz conta quantas vezes cada byte aparece, dá códigos menores aos bytes mais frequentes e grava a sequência resultante em bits.

O algoritmo de Huffman é uma codificação sem perda: a descompressão recupera exatamente os bytes originais. O projeto trabalha com um alfabeto de 256 símbolos possíveis, correspondente a todos os valores de um byte. Por isso, o conteúdo pode ser texto ou arquivo binário, sem depender de UTF-8, ASCII ou de um tipo específico de documento.

256símbolos de byte possíveis
2 leiturasfrequências primeiro; codificação depois
Sem perdaos bytes restaurados devem ser idênticos
Intuição: frequência maior, código menor
A · 0A · 0A · 0 B · 1C · 2

O desenho mostra somente a ideia. Os códigos reais dependem da árvore construída para as frequências daquele arquivo.

Razão de compressão. O programa usa R = Sc / So, em que Sc é o tamanho comprimido e So o tamanho original. Menos de 1 significa que o arquivo diminuiu; maior que 1 significa que cresceu. O cabeçalho fixo torna arquivos pequenos especialmente suscetíveis a crescer.
02 · Organização do código

Um módulo para cada responsabilidade

A interface de terminal não implementa Huffman. Ela coleta caminhos e delega o trabalho aos módulos especializados.

main.c

Menu, leitura de caminhos, extensão de saída, medição de tempo e mensagens ao usuário.

compressor.c

Orquestra as passagens pelo arquivo, o cabeçalho, a codificação, a decodificação e o tratamento de falhas.

huffman_tree.c

Cria, combina e libera nós da árvore de Huffman.

min_heap.c

Fila de prioridade própria: mantém acessível o nó de menor frequência.

dictionary.c

Percorre a árvore e armazena código, comprimento e frequência para cada byte.

bitio.c

Empacota e desempacota bits usando buffers, sem uma chamada de arquivo por bit.

Os arquivos .h definem as interfaces e os tipos compartilhados; os arquivos .c contêm as implementações. O Makefile compila o projeto com -std=c89 -Wall -Wextra -pedantic.

03 · Primeira passagem

Compressão: medir antes de codificar

Em compressor_compress, o arquivo é aberto com fopen(input_path, "rb"). A primeira leitura não escreve dados comprimidos: ela conta os bytes e preenche um vetor com 256 posições.

unsigned long frequencies[256];
unsigned long total;
unsigned char buffer[8192];

while ((count = fread(buffer, 1, sizeof(buffer), input)) != 0) {
    total += (unsigned long)count;
    for (index = 0; index < count; ++index)
        ++frequencies[buffer[index]];
}

Trecho conceitual de count_input; a implementação também verifica overflow e erros de leitura.

Por exemplo, se o byte 0x41 aparecer 500 vezes, a posição frequencies[65] recebe 500. O índice é o próprio valor numérico do byte. A leitura ocorre em blocos de 8192 bytes, reduzindo o custo de chamadas de I/O.

Por que são necessárias duas leituras?

O código precisa conhecer as frequências completas para construir os códigos antes de começar a emitir o fluxo Huffman. Depois da análise, usa fseek(input, 0, SEEK_SET) para retornar ao início e faz a segunda leitura, agora codificando. Também recalcula as frequências nessa segunda passagem e compara as tabelas; isso detecta mudanças no arquivo entre as leituras.

04 · Estrutura de dados

Heap mínimo constrói a árvore

Uma folha representa cada byte com frequência diferente de zero. Cada nó guarda frequência, símbolo mínimo da subárvore, ordem de criação e ponteiros para os filhos. Nós internos representam a soma de duas frequências e não correspondem a um byte de entrada.

typedef struct HuffmanNode {
    unsigned long frequency;
    unsigned long order;
    unsigned int minimum_symbol;
    unsigned char symbol;
    int is_leaf;
    struct HuffmanNode *left;
    struct HuffmanNode *right;
} HuffmanNode;

O processo começa com até 256 folhas no heap. Repetidamente, remove os dois menores nós, cria um pai e reinsere esse pai. Quando resta uma raiz, a árvore está pronta. O heap ordena por frequência e resolve empates por símbolo mínimo e ordem; isso torna a construção reproduzível.

Exemplo didático: A aparece 5 vezes; B aparece 2 vezes 
           [7]
          /   \
      B [2]   A [5]
        0       1

Neste exemplo, B = 0 e A = 1. O código real pode inverter os lados conforme a regra de desempate e as frequências.

Para k símbolos diferentes, a construção com heap custa aproximadamente O(k log k). Como k ≤ 256, a tabela e a árvore são pequenas mesmo que o arquivo seja grande. A função huffman_tree_free percorre recursivamente os filhos e libera cada nó.

05 · Códigos prefixados

Da árvore ao dicionário de bits

dictionary_from_tree percorre a árvore recursivamente. Ao descer para a esquerda, acrescenta 0; para a direita, acrescenta 1. Quando encontra uma folha, grava o caminho no vetor correspondente ao byte.

path[depth] = 0;
fill_dictionary(dictionary, node->left, path, depth + 1);

path[depth] = 1;
fill_dictionary(dictionary, node->right, path, depth + 1);

Esses códigos são prefixados: uma folha não pode ser ancestral de outra folha. Na decodificação, basta ler bits até encontrar uma folha; não é necessário guardar separadores entre os códigos.

Limitação real do código atual. HUFFMAN_MAX_CODE_BITS permite caminhos de até 255 bits, mas DictionaryEntry.bits tem somente 32 posições. Se uma árvore produzir código maior que 32 bits, fill_dictionary pode escrever além do vetor. Para alinhar capacidade e limite, a declaração deve ser unsigned char bits[HUFFMAN_MAX_CODE_BITS]. Corrija e teste esse ponto antes de apresentar o programa como robusto para todas as distribuições de frequência.

Uma árvore com apenas uma folha é um caso especial: o caminho normal tem comprimento zero. O programa atribui o código 0, de um bit, a esse único símbolo. Assim, cada ocorrência continua representada no fluxo e o decodificador consegue validar os bits consumidos.

06 · Persistência

O que existe dentro de um arquivo .zipz?

O cabeçalho ocupa 2062 bytes. Ele guarda informação suficiente para verificar o formato e reconstruir a árvore, sem serializar ponteiros ou depender do layout de uma struct C.

OrdemCampoTamanhoUso
1Magic UZPZ4 bytesIdentifica o formato.
2Versão1 byteAtualmente 1; distingue futuras versões.
3Tamanho original8 bytesLimita quantos bytes o decodificador deve produzir.
4Bits válidos no último byte1 byteInforma quais bits finais pertencem ao fluxo.
5256 frequências2048 bytesPermite reconstruir deterministicamente a árvore.
6Payload HuffmanVariávelCódigos empacotados; começa após o cabeçalho.

O total do cabeçalho é 4 + 1 + 8 + 1 + (256 × 8) = 2062 bytes. Os contadores são gravados em big-endian pelas funções write_ulong e read_ulong. Isso define a ordem dos bytes no arquivo, embora o maior valor representável em memória ainda dependa do tamanho de unsigned long da plataforma.

A árvore não é gravada no arquivo. O descompactador lê as frequências, chama o mesmo construtor de árvore e obtém a mesma forma porque o desempate do heap é determinístico.

Padding. O payload é escrito do bit mais significativo para o menos significativo. Se o último byte ficar incompleto, o escritor desloca os bits para a esquerda e completa o fim com zeros. O cabeçalho registra quantos bits desse último byte são válidos. Para um payload não vazio que termina exatamente numa fronteira de byte, o campo vale 8; para arquivo vazio, vale 0.
07 · Caminho inverso

Decodificar é caminhar pela árvore

compressor_decompress abre a entrada em rb e valida magic, versão, tamanho, bits válidos e frequências antes de começar a produzir o arquivo restaurado.

  1. Valida o cabeçalho. A soma das 256 frequências deve ser igual ao tamanho original; os campos truncados ou inconsistentes são rejeitados.
  2. Reconstrói a árvore. Usa a tabela do cabeçalho e o mesmo heap mínimo determinístico.
  3. Lê os bits. bit_reader_read_bit extrai um bit do byte atual, do mais significativo para o menos significativo.
  4. Segue as arestas. Bit zero significa filho esquerdo; bit um significa filho direito. Ao chegar a uma folha, emite o byte daquele símbolo e volta à raiz.
  5. Valida a saída. Compara frequências decodificadas, tamanho, padding e bytes extras; grava os bytes em blocos de 8192.
node = root;
while (!node->is_leaf) {
    bit_reader_read_bit(&reader, &bit);
    node = bit == 0 ? node->left : node->right;
}
output_buffer[output_used++] = node->symbol;

Trecho simplificado do percurso usado para cada símbolo; a implementação também trata leitura curta e erro de I/O.

08 · Robustez e limites

Casos de borda que o projeto considera

CasoTratamento
Arquivo vazioSem árvore e sem payload; gera cabeçalho e restaura zero bytes.
Um único byte distintoUsa código de um bit por ocorrência e valida que cada bit é zero.
Entrada inexistentefopen falha; a operação retorna erro.
Magic ou versão incorretosO cabeçalho é rejeitado antes da criação da saída.
Arquivo truncado/inconsistenteFalha de leitura, frequências divergentes ou padding inválido causam erro.
Destino já existeO programa recusa a operação para evitar sobrescrever o arquivo existente.
Falha ao escreverAs escritas e o fechamento são verificados; uma saída parcial da operação é removida.

A proteção contra sobrescrita faz uma verificação com output_is_new e depois abre o destino com fopen(..., "wb"). Em um cenário concorrente, outro processo poderia criar o nome entre essas duas operações; C89 não fornece uma abertura exclusiva portável. É uma limitação a conhecer, não uma garantia de segurança contra concorrência.

O tamanho em memória usa unsigned long. O cabeçalho reserva 8 bytes, mas uma plataforma na qual unsigned long seja menor não consegue processar todos os valores que cabem no formato de 64 bits. O código verifica overflow ao ler os campos.

O que falta para detectar qualquer corrupção?

As verificações estruturais detectam muitos erros, mas não garantem que cada bit veio intacto: uma alteração pode, em princípio, produzir outra sequência com as mesmas frequências. Uma extensão recomendada é gravar um checksum, como CRC-32, e recalculá-lo durante a descompressão.

09 · Avaliação

O que comparar com gzip

Para uma avaliação justa, use os mesmos arquivos, a mesma máquina e várias execuções. Registre tamanho original, tamanho comprimido, razão Sc/So, tempo de compressão e tempo de descompressão. O comando cmp original restaurado confirma igualdade byte a byte; código de saída zero indica que os arquivos são iguais.

PerfilO que evidenciaResultado esperado
Baixa redundância / aleatórioDistribuição de bytes próxima de uniforme.Huffman quase não encurta; o cabeçalho pode fazer crescer.
Redundância média / texto variadoAlguns bytes frequentes, com repetições locais.Huffman pode reduzir; gzip tende a explorar também padrões.
Alta redundância / frase repetidaLongas sequências reaparecem.Huffman reduz o viés de bytes; gzip geralmente ganha com LZ77.

Em uma execução local dos exemplos de teste, o arquivo aleatório de 1.048.576 bytes resultou em 1.050.638 bytes no Zipz e 1.048.764 bytes no gzip. Um texto de 960.000 bytes resultou em 543.812 bytes no Zipz e 51.298 bytes no gzip. Uma sequência repetida de 1.440.000 bytes resultou em 789.562 bytes no Zipz e 4.283 bytes no gzip. São resultados ilustrativos desses arquivos específicos, não uma promessa para todos os dados.

O gzip combina LZ77, que representa ocorrências repetidas como referências a trechos anteriores, com codificação Huffman. O UFABC Zipz implementa somente Huffman por byte. Por isso, o Zipz pode se aproximar quando há distribuição de bytes favorável sem muitas sequências repetidas; em texto altamente repetitivo, normalmente se distancia bastante.

Comandos de referência para GNU/Linux 
# Comprimir com gzip sem alterar o original
/usr/bin/time -f 'gzip: %e s' gzip -c entrada > entrada.gz

# Comparar os tamanhos
wc -c entrada entrada.zipz entrada.gz

# Descomprimir gzip e conferir os bytes
/usr/bin/time -f 'gzip descompressao: %e s' gzip -dc entrada.gz > gzip-restaurado
cmp entrada restaurado
cmp entrada gzip-restaurado

O tempo mostrado pelo menu do Zipz usa clock(); para comparação experimental, o cronômetro externo deve envolver o programa Zipz e o gzip do mesmo modo.

10 · Fechamento

Roteiro curto para explicar ao grupo

“O UFABC Zipz é um compressor sem perda baseado em Huffman para bytes. Na primeira leitura, contamos as frequências. Com elas, um heap mínimo constrói a árvore combinando sempre os dois símbolos ou subárvores menos frequentes. Um percurso recursivo gera códigos prefixados: esquerda é zero, direita é um. Na segunda leitura, cada byte vira seu código, que é empacotado em bits. O cabeçalho guarda um identificador, versão, tamanho original, frequências e informação dos bits finais. Para descomprimir, validamos o cabeçalho, reconstruímos a mesma árvore e seguimos os bits até as folhas, recuperando cada byte. O formato é simples de estudar, mas o cabeçalho tem custo fixo e o algoritmo não explora repetições longas como o LZ77 usado pelo gzip.”

Extensões possíveis

  • Checksum: detectar corrupção com CRC-32 no cabeçalho ou no final do fluxo.
  • Modo verboso: exibir frequências, comprimentos dos códigos e estatísticas.
  • Huffman de palavras: requer definir tokens e preservar separadores e bytes originais sem perda.
  • LZ77 + Huffman: transformar sequências em literais ou referências e versionar o formato.
  • Busca por blocos: adicionar pontos de reinício ou índice; o formato atual precisa decodificar desde o início.

Para estudar o código-fonte, comece em main.c, siga para compressor.c e depois acompanhe as chamadas de árvore, dicionário e bits. Consulte também o leia-me.txt para compilação e uso.
